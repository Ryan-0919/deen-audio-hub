# 商城支付体系设计

## 1. 文档目标

本文件不只讨论“如何接回调”，而是把商城支付体系完整定义出来，解决以下问题：

- 商城订单和支付单的边界怎么划分
- 一期应该支持哪些支付渠道
- 统一支付入口怎么设计
- 支付状态机怎么定义
- 支付成功后如何驱动课程开通和实物履约
- 退款、对账、风控和异常补偿怎么留好扩展位

本稿的定位是商城支付体系总纲，和 [09-商城支付与回调设计.md](D:/Desktop/my_code/音频系统/video-hub/doc/商城设计文档/09-商城支付与回调设计.md) 的关系如下：

- `09` 偏回调、幂等、履约触发
- `10` 偏体系、分层、渠道、状态机、扩展能力

## 2. 支付体系的设计原则

### 2.1 订单中心和支付中心分离

商城里至少有两个核心对象：

- 交易订单：用户买了什么，多少钱，收货地址是什么
- 支付单：用户准备用什么渠道付，平台返回了什么交易号，当前支付到哪一步

因此不建议只用 `ShopOrder` 一张表承载全部支付语义。

最低可接受的一期方案是：

- `ShopOrder` 负责交易主语义
- `ShopPaymentRecord` 负责支付主语义

### 2.2 对外多渠道，对内统一语义

对外可能接：

- 微信 JSAPI
- 微信 H5
- 支付宝 WAP
- 后续小程序支付

但对内统一抽象为：

- `channel`
- `paymentMethod`
- `payStatus`
- `transactionNo`
- `callbackStatus`
- `paidAt`

这样后续切换渠道时，订单逻辑和履约逻辑不用推倒重做。

### 2.3 支付成功不等于订单完成

在你的商城场景里，这一点非常重要。

- 纯虚拟商品：支付成功后还要开课
- 纯实物商品：支付成功后还要发货
- 组合商品：支付成功后要同时开课和发货

所以支付体系只能推进订单状态，不能直接把订单写死成完成。

### 2.4 一期先做单订单单支付单

一期不建议一开始就上复杂模式：

- 一个订单拆多个支付单
- 合单支付
- 多次补差价
- 多种渠道并行竞争同一订单

一期建议明确：

- 一个 `ShopOrder` 对应一条主 `ShopPaymentRecord`
- 只允许主支付单成功一次

## 3. 一期支付范围建议

## 3.1 一期建议支持的渠道

考虑你这个项目用户以手机端为主，且存在扫码跳转场景，一期建议优先顺序如下：

1. `wechat_jsapi`
2. `wechat_h5`
3. `alipay_wap`

### 为什么先这样排

- `wechat_jsapi` 适合用户在微信内直接完成支付
- `wechat_h5` 适合用户在普通手机浏览器里直接跳转微信支付
- `alipay_wap` 适合用户在普通手机浏览器里直接跳转支付宝支付

### 一期明确不支持的支付入口

- 微信 Native 二维码支付
- 网页二维码收银台
- 支付宝电脑网站支付
- PC 浏览器直接收银台支付

### 页面展示策略

为了保证“用户直接进入平台内支付”，前端支付按钮应按打开环境动态显示：

- 微信内打开：只展示 `微信支付`
- 普通手机浏览器打开：展示 `微信支付` 和 `支付宝支付`
- PC 浏览器打开：不展示正式支付按钮，提示用户改用手机打开

## 3.2 一期建议不支持的支付能力

- 分期支付
- 余额支付
- 组合支付
- 订金尾款
- 代付
- 分账
- 多商户结算

这些都不是你现在这个商城闭环最核心的能力。

## 4. 支付体系分层设计

建议把支付体系拆成 5 层。

### 4.1 交易层

职责：

- 创建商城订单
- 冻结库存
- 保存订单快照
- 触发支付单创建

核心对象：

- `ShopOrder`
- `ShopOrderItem`

### 4.2 支付中心层

职责：

- 创建支付单
- 选择支付渠道
- 生成支付参数
- 接收异步回调
- 推进支付状态

核心对象：

- `ShopPaymentRecord`
- `ShopRefundRecord`

### 4.3 渠道适配层

职责：

- 对接微信、支付宝等第三方 SDK 或 HTTP 接口
- 统一封装下单、验签、查询单、退款单

建议抽象接口：

- `createPayment()`
- `verifyCallback()`
- `parseCallback()`
- `queryPayment()`
- `createRefund()`

### 4.4 履约层

职责：

- 支付成功后发放课程权限
- 创建待发货记录
- 失败时记录异常状态

核心对象：

- `ShopDigitalFulfillment`
- `ShopShipment`

### 4.5 对账与补偿层

职责：

- 拉平台账单
- 查询异常单
- 补做发课
- 补做发货
- 标记支付异常

这一层一期可以先简化，但设计上必须预留。

## 5. 一期推荐支付模型

## 5.1 交易订单模型

继续使用现有文档中的：

- `ShopOrder`
- `ShopOrderItem`

### 订单关注的问题

- 买了什么
- 总价多少
- 收货地址是什么
- 当前订单整体走到哪一步

订单不应该承载过多第三方支付渠道细节。

## 5.2 支付单模型

一期继续以 `ShopPaymentRecord` 为主，但建议字段语义再明确一些。

建议字段：

- `id`
- `orderId`
- `channel`
- `method`
- `status`
- `transactionNo`
- `outTradeNo`
- `payAmount`
- `requestPayload`
- `callbackPayload`
- `callbackVerified`
- `callbackAt`
- `paidAt`
- `failReason`
- `createdAt`
- `updatedAt`

### 字段说明

- `channel`：微信、支付宝等渠道标识
- `method`：H5、JSAPI、PAGE 等支付方式
- `outTradeNo`：我方传给支付平台的商户单号
- `transactionNo`：支付平台返回的交易号
- `requestPayload`：发起支付时的原始参数
- `callbackPayload`：回调原始报文

### 一期落地建议

如果暂时不想改动过大，也可以先不拆 `method` 字段，直接把：

- `wechat_jsapi`
- `wechat_h5`
- `alipay_wap`

直接记在 `channel` 里。

但从长期看，最好还是：

- `channel = wechat`
- `method = h5`

## 5.3 退款单模型

现有 `ShopRefundRecord` 设计方向可以保留，但支付体系层面建议明确它的职责：

- 退款申请记录
- 退款状态记录
- 第三方退款单号记录
- 退款结果回执记录

建议补充字段语义：

- `refundNo`
- `paymentRecordId`
- `channelRefundNo`
- `refundAmount`
- `status`
- `requestPayload`
- `callbackPayload`
- `refundedAt`

## 6. 支付状态机设计

## 6.1 支付单状态

一期建议支付单状态不要只有 `unpaid / paid / failed / refunded` 四个，而是最好在系统内部区分得更细。

建议内部状态：

- `created`
- `paying`
- `paid`
- `failed`
- `closed`
- `refund_pending`
- `refunded`
- `refund_failed`

### 为什么要细一点

因为实际支付过程中会出现：

- 已创建支付单，但前端还没拉起
- 用户正在支付中
- 支付超时关闭
- 已支付但未退款
- 退款处理中

如果都压缩成非常少的状态，后续排查问题会很痛苦。

### 一期折中方案

如果数据库暂时只保留粗状态，也建议在服务层内部保留更细的流程状态判断。

## 6.2 订单状态与支付状态关系

推荐关系如下：

| 订单状态 | 支付状态 | 说明 |
| --- | --- | --- |
| `pending_payment` | `unpaid` | 已下单待支付 |
| `paid` | `paid` | 已支付，待履约 |
| `partially_fulfilled` | `paid` | 已支付，部分履约完成 |
| `completed` | `paid` | 支付成功且履约完成 |
| `cancelled` | `unpaid` 或 `failed` | 未支付关闭或失败关闭 |
| `refunding` | `paid` | 退款处理中 |
| `refunded` | `refunded` | 已完成退款 |

## 7. 不同商品类型的支付处理

## 7.1 纯虚拟商品

支付成功后：

1. 标记订单已支付
2. 创建或更新 `ShopDigitalFulfillment`
3. 发放课程权限
4. 权限发放成功后，订单可直接进入 `completed`
   或者先 `paid` 再由履约任务推进到 `completed`

一期建议：

- 走统一履约任务
- 不在支付回调里直接写死完成

## 7.2 纯实物商品

支付成功后：

1. 标记订单已支付
2. 生成待发货任务
3. 后台发货后更新物流状态
4. 用户确认收货或签收后完成订单

## 7.3 组合商品

支付成功后：

1. 标记订单已支付
2. 创建数字履约
3. 创建实物待发货
4. 数字履约成功后进入 `partially_fulfilled`
5. 发货签收后进入 `completed`

这类商品是支付体系设计里最不能偷懒的一类，因为它天然要求：

- 交易状态
- 支付状态
- 数字履约状态
- 实物履约状态

四者分开。

## 8. 支付渠道抽象建议

## 8.1 渠道接口定义

建议在 `server/lib/payment/channels` 下做统一适配器。

接口可以统一成：

```js
createPayment(order, paymentRecord)
verifyCallback(request)
parseCallback(request)
queryPayment(paymentRecord)
createRefund(refundRecord)
```

## 8.2 建议目录结构

```text
server/lib/payment/
  index.js
  constants.js
  service.js
  state-machine.js
  callback.js
  refund.js
  reconcile.js
  channels/
    wechat.js
    alipay.js
```

## 8.3 建议路由结构

```text
server/routes/payment.js
```

建议提供：

- `POST /api/payment/callback/:channel`
- `GET /api/user/shop/orders/:orderId/pay`
- `POST /api/admin/shop/orders/:orderId/refund`
- `GET /api/admin/shop/payments/:paymentId`

## 9. 下单与支付发起流程

建议流程如下：

1. 用户提交商城订单
2. 后端校验库存、商品状态、价格
3. 创建 `ShopOrder`
4. 创建 `ShopPaymentRecord`
5. 按渠道生成支付参数
6. 返回给前端支付参数
7. 前端拉起支付
8. 用户支付
9. 平台异步回调
10. 后端更新支付状态和订单状态
11. 触发履约

### 一期建议

不要让前端自己拼支付参数，也不要让订单接口和支付 SDK 强耦合。

更稳的方式是：

- 订单接口只产出订单
- 支付接口或支付服务只产出支付参数

并且前端不要自己生成二维码或收银台链接，统一只消费三种平台支付参数：

- `wechat_jsapi`
- `wechat_h5`
- `alipay_wap`

## 10. 回调、查询与主动补偿

支付体系不能只依赖异步回调。

建议同时保留三条确认路径：

- 异步回调
- 主动查询支付结果
- 后台人工补偿

### 为什么要这样

因为真实线上经常出现：

- 回调丢失
- 回调延迟
- 验签失败但实际上用户已支付
- 平台成功但本地事务失败

因此建议：

- 回调为主
- 主动查询为补
- 后台人工处理为兜底

## 11. 退款体系建议

## 11.1 一期退款策略

一期建议先支持：

- 后台人工发起退款
- 记录退款单
- 等待支付平台退款结果
- 更新订单和退款状态

先不做：

- 用户自助退款申请流程全自动审批
- 自动按商品明细拆分复杂退款

## 11.2 退款和履约的关系

不同商品退款策略必须区分：

- 纯虚拟商品：若已开课，需定义是否允许退款
- 纯实物商品：若已发货，需定义是否先退货再退款
- 组合商品：需定义部分退款还是整单退款

### 一期建议

先把业务规则写死，避免系统过度通用：

- 已开课的纯虚拟商品默认走人工审核
- 已发货的实物商品默认走人工审核
- 组合商品退款默认人工处理，不做自动拆分

## 12. 对账体系建议

## 12.1 一期最小对账能力

建议至少具备：

- 每日查询当天支付成功订单
- 与支付平台账单做比对
- 找出漏单、重单、金额不一致单
- 输出异常清单

## 12.2 对账结果的异常分类

建议分成：

- 本地已支付，平台无记录
- 平台已支付，本地未入账
- 金额不一致
- 平台已退款，本地未退款
- 本地已退款，平台未退款

## 12.3 对账落地方式

一期可以先不做复杂页面，先做：

- 后台导出异常表
  或
- 每日定时任务写日志和异常表

## 13. 风控与安全建议

支付体系最基本的安全要求：

- 严格验签
- 校验订单金额
- 校验订单状态
- 限制回调重复处理
- 保存原始请求和响应
- 后台敏感操作必须写审计日志

### 额外建议

- 支付配置不要放前端
- 商户密钥只保存在服务端环境变量
- 后台人工改支付状态必须有高权限限制

## 14. 支付配置建议

建议单独增加支付配置概念，不与普通系统配置混写。

一期可以先通过环境变量驱动：

- `PAY_PROVIDER`
- `WECHAT_PAY_MCH_ID`
- `WECHAT_PAY_APP_ID`
- `WECHAT_PAY_API_V3_KEY`
- `WECHAT_PAY_PRIVATE_KEY`
- `WECHAT_PAY_CERT_SERIAL_NO`
- `ALIPAY_APP_ID`
- `ALIPAY_PRIVATE_KEY`
- `ALIPAY_PUBLIC_KEY`
- `PAY_NOTIFY_BASE_URL`

后续如果后台需要可视化配置，再新增：

- `PaymentConfig`

## 15. 与现有项目的结合点

当前项目最关键的结合边界如下：

- 商城支付系统只负责“收款成功”和“触发履约”
- 课程系统只负责“课程是否可见”和“学习逻辑”
- 实物发货系统只负责“物流状态”

支付系统支付成功后，真正要落到现有业务里的动作只有两类：

1. 写商城支付记录和订单状态
2. 写课程权限和发货任务

不要让支付层直接接管课程展示逻辑，否则后面会把商城和课程系统绑死。

## 16. 一期建议实施顺序

推荐顺序如下：

1. 明确支付渠道和环境变量
2. 完成 `ShopPaymentRecord` 字段收敛
3. 实现统一支付服务层
4. 接一个主支付渠道
5. 接支付回调与幂等
6. 打通自动开课和待发货
7. 补后台退款和异常补偿
8. 最后补对账能力

## 17. 结论

对你这个商城来说，支付体系不是单独一个“支付按钮”，而是四件事的组合：

- 交易建单
- 渠道收款
- 支付确认
- 履约推进

如果这四件事一开始就拆清楚，后面无论你卖的是：

- 单独音频课程
- 课程加书籍
- 单独实物

都可以在同一套支付体系里跑，不需要再做第二套逻辑。
