# 商城支付与回调设计

## 1. 文档目标

本文件用于明确商城一期支付相关的设计边界，重点解决以下问题：

- 如何生成支付单
- 如何接收支付回调
- 如何避免重复回调导致重复开课
- 支付成功后如何推进虚拟和实物履约
- 如何做异常补偿和对账

## 2. 一期支付设计原则

### 2.1 统一订单，分层处理

一期建议坚持三层分离：

- `ShopOrder` 负责交易主状态
- `ShopPaymentRecord` 负责支付记录
- `ShopDigitalFulfillment` / `ShopShipment` 负责履约结果

不要把“已支付”“已开课”“已发货”全部塞进一个字段里，否则组合商品会很快失控。

### 2.2 渠道可切换，内部模型不变

虽然一期可能只先接一个支付渠道，但内部设计必须保持通用：

- `channel`
- `transactionNo`
- `rawPayload`
- `paidAt`

这样后续新增微信、支付宝、小程序支付时，不需要重写整套订单模型。

### 2.3 支付回调必须幂等

支付平台回调可能：

- 重复通知
- 乱序通知
- 在用户主动查询结果后才通知

因此支付处理必须做到：

- 多次回调只认一次成功
- 已成功订单重复回调只记录日志，不重复发课
- 履约失败不能影响支付回调响应的幂等性设计

## 3. 一期推荐支付流程

### 3.1 提交订单

用户提交订单后：

1. 校验商品、SKU、库存、价格
2. 创建 `ShopOrder`
3. 创建 `ShopOrderItem`
4. 创建一条 `ShopPaymentRecord`
5. 锁定库存
6. 返回订单号和支付参数

### 一期建议

- 订单超时未支付自动取消
- 超时后释放库存
- 超时时间建议 30 分钟

### 3.2 拉起支付

根据前端场景不同，可返回：

- 微信 JSAPI 支付参数
- 微信 H5 支付参数
- 支付宝 WAP 支付参数

建议由统一方法生成：

- 输入：`orderId`、`channel`
- 输出：`paymentParams`

一期明确不返回：

- 网页二维码支付链接
- PC 收银台支付二维码
- 支付宝电脑网站支付页

前端环境建议：

- 微信内：使用 `wechat_jsapi`
- 普通手机浏览器：使用 `wechat_h5` 或 `alipay_wap`
- PC 浏览器：直接提示改用手机支付

### 3.3 支付平台异步回调

支付平台回调后：

1. 验签
2. 解析订单号
3. 查询本地订单与支付记录
4. 校验支付金额
5. 校验回调状态是否成功
6. 在事务内更新支付状态和订单状态
7. 触发履约
8. 记录回调日志
9. 按平台要求返回成功响应

## 4. 状态流转建议

### 4.1 订单状态

建议使用：

- `pending_payment`
- `paid`
- `partially_fulfilled`
- `completed`
- `cancelled`
- `refunding`
- `refunded`

### 4.2 支付状态

建议使用：

- `unpaid`
- `paid`
- `failed`
- `refunded`

### 4.3 履约状态

数字履约：

- `pending`
- `success`
- `failed`

物流发货：

- `pending`
- `shipped`
- `in_transit`
- `signed`
- `failed`

### 4.4 组合商品完成判定

对于 `hybrid` 商品：

- 数字权益已发放成功
- 实物已签收或至少达到你定义的完成条件

只有同时满足，订单才进入 `completed`。

如果数字权益已发放但实物未发货，订单应处于：

- `paid`
  或
- `partially_fulfilled`

建议一期直接使用 `partially_fulfilled`，语义更清晰。

## 5. 支付回调接口设计

### 5.1 回调地址

建议统一为：

- `POST /api/payment/callback/:channel`

示例：

- `/api/payment/callback/wechat_jsapi`
- `/api/payment/callback/wechat_h5`
- `/api/payment/callback/alipay_wap`

### 5.2 回调处理输入

输入来源：

- 支付平台原始请求体
- 支付平台请求头中的签名信息
- 支付平台交易号
- 平台订单号或商户订单号

### 5.3 回调处理输出

必须按支付平台要求返回成功标识。

例如：

- 微信返回固定成功文本
- 支付宝返回固定成功文本

这里不能沿用普通业务接口的 JSON 返回结构，而要按平台协议返回。

## 6. 幂等处理设计

### 6.1 幂等核心规则

同一笔支付回调多次到达时：

- 第一次成功处理，完成支付入账与履约触发
- 后续重复回调直接识别为已处理
- 不重复创建 `UserCoursePermission`
- 不重复创建发货任务

### 6.2 幂等判断依据

建议综合以下字段判断：

- `ShopOrder.orderNo`
- `ShopPaymentRecord.transactionNo`
- `ShopPaymentRecord.status`

### 补充建议

- 给 `transactionNo` 建索引
- 若支付平台保证全局唯一，可考虑唯一约束

### 6.3 事务建议

支付回调核心变更应放进数据库事务中：

1. 锁定订单
2. 更新支付记录
3. 更新订单支付状态
4. 写入支付成功时间
5. 创建履约任务或直接履约

这样可以降低并发回调下的重复处理风险。

## 7. 支付成功后的履约设计

### 7.1 虚拟商品

支付成功后：

1. 根据 `ShopOrderItem` 快照解析绑定课程
2. 向 `UserCoursePermission` 写入课程权限
3. 已存在权限则跳过
4. 写入 `ShopDigitalFulfillment`
5. 状态改为 `success`

注意：

- 课程权限发放成功，不代表课程立刻可见
- 课程可见性仍受原课程系统 `Course.status` 与开放时间控制

### 7.2 实物商品

支付成功后：

1. 订单进入待发货
2. 后台发货页可见该订单
3. 管理员录入物流公司和单号
4. 创建 `ShopShipment`
5. 用户侧订单页展示物流状态

### 7.3 组合商品

支付成功后同时执行：

- 虚拟权益发放
- 实物待发货创建

因此组合商品不建议简单写成“支付成功即完成”。

## 8. 异常与补偿策略

### 8.1 支付成功但发课失败

处理建议：

- 保持订单支付成功
- `ShopDigitalFulfillment.status = failed`
- 记录 `errorMessage`
- 后台可做人工重试

不要因为发课失败就把支付状态改回未支付。

### 8.2 支付成功但发货任务创建失败

处理建议：

- 订单仍保持 `paid`
- 记录异常日志
- 后台订单页标记为“待处理异常”
- 支持管理员补建发货单

### 8.3 回调早于用户查询

这是正常情况，用户主动刷新订单详情时应直接看到最新状态。

### 8.4 用户已看到支付成功页，但回调延迟

建议前端同时做两件事：

- 支付完成页轮询订单状态
- 等待异步回调把订单最终推进

不要只依赖前端跳转结果判断支付成功。

## 9. 安全设计

支付相关至少要做到：

- 验签
- 校验订单归属和订单金额
- 校验订单状态是否允许收款
- 记录原始回调报文
- 限制内部手工改支付状态的权限

后台若要支持人工确认支付，建议单独做高权限操作，并强制记录审计日志。

## 10. 日志与对账设计

### 10.1 建议记录的日志

- 发起支付日志
- 支付回调接收日志
- 验签结果日志
- 幂等命中日志
- 数字履约结果日志
- 发货任务创建日志

### 10.2 对账建议

一期即使不做完整自动对账，也建议至少预留每日对账任务：

1. 查询当天 `paid` 订单
2. 对比支付平台账单
3. 标出金额异常、漏单、重复单
4. 导出后台核查结果

## 11. 一期建议不做的复杂能力

- 多次分账
- 合单支付后拆单清结算
- 自动退款原路返回
- 多支付单并行竞争同一订单
- 多币种
- 多商户支付主体

这些都会明显拉高一期复杂度，不建议现在就引入。

## 12. 推荐落地顺序

建议按以下顺序接入支付能力：

1. 先完成订单模型和提交订单
2. 再完成支付单生成
3. 再完成支付回调验签和幂等
4. 再完成自动开课
5. 最后完成后台异常补偿和对账

## 13. 与当前项目的结合点

本项目商城支付成功后的关键落点只有两个：

- 写 `ShopPaymentRecord`
- 写 `UserCoursePermission`

其中：

- 交易结果归商城系统负责
- 课程内容是否可见归现有课程系统负责

这个边界要一直保持清晰，后续商城扩展时才不会把课程系统拖乱。
